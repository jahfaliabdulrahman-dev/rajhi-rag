# SECURITY

## Never post real data

This repository is PUBLIC and permanently indexed. Do not open an issue or a
pull request containing — in the body, a comment, a screenshot or a commit
message:

- a real bank statement, or any page/row/amount copied from one;
- an account, card or IBAN number, in any digit script, spaced or split;
- a name, address or national id from a statement;
- an API key, token or `.env` file.

Synthetic fixtures live in `data/sample/` and are generated by
`scripts/make_synthetic_statement.py` — use those in reports.

## What enforces what — declared, not assumed

The amount check is **not** one mechanism with two runtimes: it has two surfaces with **different
powers**, and the difference is the point (a green badge must never be quotable as «the amounts are clean»).

| surface | what it DOES | what it does NOT do |
|---|---|---|
| `.githooks/pre-push` (local) | runs the static gate, `publish_guard` and the **amount guard** over exactly the refs being pushed (`stdin`), and **blocks** a range that adds one occurrence over the published baseline | it runs only where the hook is installed (`git config core.hooksPath .githooks`) and where the local evidence exists (`data/` is gitignored; resolved via `git --git-common-dir`, so a worktree or a subdirectory still finds it) |
| CI (`publish-guard.yml`) | `publish_guard` over tree + history + messages; the tracking audit (key/manifest/redaction map); the real-data path check | the **amount guard declares rather than enforces**: the keyed manifest is deliberately never published, because a fingerprint over an enumerable domain plus a published key is not a mask. CI prints what it therefore did NOT check. |
| `docs/security/amount-baseline.json` | per-file occurrence COUNTS — the ratchet's frozen line, public by design | it carries no values and no fingerprints, so it cannot be used to recover an amount |

## Reporting a vulnerability

Use **GitHub Security Advisories** ("Report a vulnerability" on the Security
tab) for anything sensitive. Ordinary bugs belong in a normal issue.

The publish guard (`tools/publish_guard.py`) runs on every push, on CI, and
over the whole history; its severity model, allowlist and — importantly — the
list of things it *cannot* see are documented at the top of that file:
its self-exclusion is a hole, so the guard's own text is policed by the test
suite instead.
