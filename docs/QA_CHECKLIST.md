## ٢. الفحص اليدوي (خمس دقائق)

1. **نفس السطح الذي سيستخدمه المالك** — افتح `http://127.0.0.1:7860` بمتصفح حقيقي وامشِ المسار كاملاً (رفع → زر → نتيجة). فحص API وحده لا يكفي.
2. **القيم مقابل الأصل** — افتح رندر الصفحة عينياً وقارن أول ٣ صفوف بمخرجات التطبيق. السلسلة «النظيفة» لا تكشف انزياحاً موحّداً (×100) — المقارنة العينية إلزامية (وقد صار أوراكل الفوتر يلتقط الأشكال الموحّدة آلياً، لكن العين تبقى الحكم الأخير).
3. **سطح واحد فقط** — لا قوالب/عروض توضيحية موازية أمام المالك؛ أي سطح ثانٍ يجب أن يحوّل أو يُغلق.
4. **الخصوصية** — كشوف حقيقية لا تُرفع إلى git ولا تُشارك مع طرف ثالث ولا يُبنى عليها أي سطح عام؛ الـfixture العام اصطناعي. **وبصراحة كاملة:** صور كل صفحة تُرسل إلى **مزوّد القراءة البصرية السحابي** في الطلب نفسه — وهذا قيد مُعلَن (يُعالج بمسار معالجة محلية، لا يُنكر)، فلا تعرض على عميل حقيقي معالجة لم يوافق عليها.
5. **الخدمات الدائمة** — `launchctl list | grep rajhi` (app + redirect + healthcheck). بعد أي تعديل كود: أعِد التثبيت عبر `tools/install_services.sh` إن لزم، **ولا تفعل `kickstart` أثناء احتمال تشغيل المالك** — إعادة التشغيل تقتل مهمته الجارية.
6. **التوثيق** — commit + سطر في `references/rajhi-rag-state.md`: ما فُحص وما لم يُفحص، وبأي دليل.

## ٣. قبل أي push — حزمة النشر الآمن (G3)

```bash
python tools/publish_guard.py --tree --history   # يجب: 0 BLOCK قبل أي push
```

- **التفعيل مرة واحدة لكل نسخة clone:** `git config core.hooksPath .githooks` (هوك pre-push يشغّل الفحص تلقائياً)، وحاجز CI في `.github/workflows/publish-guard.yml`.
- **ممنوعات الرفع (BLOCK):** مسارات منزل مطلقة · اسم ملف الكشف الأصلي · الأسماء العائلية الواردة في الكشف · سلاسل أرقام ≥10 (حسابات/بطاقات) · أي ملف تحت `data/local_sample/` · ملفات `.env` · وسائط غير مسموحة.
- **الاستثناءات:** فقط في `.publish-allowlist` وبسبب مكتوب — لا استثناء بلا مبرر.
- **عند اكتشاف BLOCK تاريخي:** أعِد كتابة التاريخ بـ `git-filter-repo --replace-text` (مثال منفَّذ: تنظيف fixtures قديمة قبل أول نشر) ثم أعد الفحص.
